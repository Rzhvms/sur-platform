# Банковские демоданные

Сценарий — вымышленный банк «Северный Контур»: дистанционные счета и кредитование, СБП/карточные платежи, ПОД/ФТ и регуляторная отчётность. Набор предназначен для тестовых клиентских баз и отображается обычными API, без режима подмены ответов фронтенда.

## Включение

В `Api/appsettings.json` по умолчанию:

```json
{
  "ActivateDemoDataSeed": false,
  "DemoDataSeedPassword": ""
}
```

Для прямого запуска задайте переменную окружения `ActivateDemoDataSeed=true` либо измените настройку через конфигурацию запуска IDE. Для Compose те же имена переменных проброшены в backend:

```env
ActivateDemoDataSeed=true
```

После сборки обновлённого бэкенда и его перезапуска набор запишется отдельно в каждую базу из доверенного каталога `Clients`. Подготовка выполняется после миграций и начальной настройки администратора, до установки readiness клиента. При `Operations__PauseOutbound=true` автоматическое заполнение также приостановлено для восстановления базы.

Если нужны входы под деморолями, до **первого** включения задайте `DemoDataSeedPassword` через окружение/секрет хоста. Ограничения: 8–256 символов, не только пробелы. Исходного пароля в наборе и appsettings нет; для каждой новой записи сохраняется отдельный хеш с солью. Пароль является постоянным тестовым паролем, не временной административной выдачей. Без него демопрофили и оргсвязи создаются, но учётные данные для входа не создаются. Администратор позднее может выдать таким пользователям временный доступ обычной командой.

Изменение DemoDataSeedPassword после установки не сбрасывает пароли. Повторная выдача через UI требует смены при первом входе и действует 10 дней по общему контракту. Учётные записи с ролью ADMIN сид не создаёт; для управления используйте существующего администратора клиента.

## Состав

| Данные | Количество |
| --- | ---: |
| Дирекции | 3 |
| Бизнес-процессы с действующими владельцами | 6 |
| Объекты с денежной ставкой простоя | 3 |
| Демопрофили и сотрудники | 11 |
| Группы опасностей / опасности / категории | 3 / 6 / 3 |
| Риски | 18: по 3 в каждой из 6 колонок |
| Оценки | 15: текущие и исторические, включая нулевой балл |
| Меры | 12: черновик, согласование, согласовано, ожидание, выполнение, холд, готово и отменено |
| Назначения исполнителей | 8 |
| Комментарии риска / меры | 18 / 12 |
| Открытые пересмотры с завершённым источником | 3 |

Пользователи используют только зарезервированный домен `bank-demo.invalid`:

| Роль | Email |
| --- | --- |
| CEO | ceo@bank-demo.invalid |
| RISK_SPECIALIST | risk-specialist@bank-demo.invalid |
| DIRECTOR | retail-director@bank-demo.invalid, payments-director@bank-demo.invalid, compliance-director@bank-demo.invalid |
| OWNER | retail-owner@bank-demo.invalid, payments-owner@bank-demo.invalid, compliance-owner@bank-demo.invalid |
| EMPLOYEE | retail-employee@bank-demo.invalid, payments-employee@bank-demo.invalid, compliance-employee@bank-demo.invalid |

Дирекции, роли и назначения согласованы: владельцы и исполнители принадлежат дирекции процесса; у сотрудника одна активная запись; специалист имеет отдельные назначения в трёх дирекциях. Если у клиента уже есть действующее назначение CEO, оно сохраняется, а демонстрационный CEO получает только роль без замены существующего назначения. Всего добавляется 6 или 7 организационных назначений.

Оценки рассчитываются существующим `AssessmentCalculation`, а не копируются как произвольные баллы. Действующая денежная шкала и границы принятия клиента сохраняются; начальная шкала публикуется только при отсутствии любой опубликованной шкалы. При необычных границах принятия принятый риск адаптируется так, чтобы не оказаться в TREATMENT_REQUIRED. Поэтому конкретные цвета и баллы могут отличаться от шаблона на уже настроенном клиенте. Для риска с объектом используются часы простоя и его ставка. В пересмотре/закрытом состоянии оценка историческая, а не текущая.

Снимки согласования мер используют фактические пороги клиента. Для мер на согласовании/согласованных стоимость при необходимости поднимается до порога. Историческое решение ссылается на уполномоченного владельца, директора либо действующего CEO; инициатором системной загрузки в журнале остаётся «Система» с источником DEMO_SEED. История и снимки доступны с момента загрузки, даже если отображаемые даты карточек расположены раньше.

Относительные даты смещаются к первому запуску: риски выглядят недавно обновлёнными, сроки мер — будущими. Повторный запуск не сдвигает даты заново. Файлы MinIO, внешние задачи Jira, webhook-секреты, активные расписания и реальные сообщения не создаются; существующие интеграции не перенастраиваются. Наличие набора не подтверждает сквозной обмен с внешними системами.

## Транзакция и повторный запуск

Миграция `202611260100` создаёт только таблицу маркера `DemoDataSeedDal`. При false бизнес-данные не добавляются. При true репозиторий получает общий advisory-lock административных/организационных команд и проверяет маркер набора №1. Все вставки, снимки, поручения журнала и маркер сохраняются одной транзакцией. Второй экземпляр приложения ждёт тот же lock и после коммита пропускает уже применённый набор.

Имена демонстрационных справочников и оргединиц имеют префикс «Северный Контур», чтобы не занимать общие названия вроде «Операционные». Вставки используют стабильные UUID из пространства `ba4c0001-*`. Нет upsert, удаления или обновления ранее существовавших бизнес-записей. При конфликте ID, email, уникального имени или недопустимой конфигурации вся загрузка откатывается, а клиент не объявляется готовым. Другой клиент не используется как резервный. Выключение флага **не удаляет** созданные данные. Редактирование через UI и смена пароля сохраняются при повторном старте.

Не удаляйте маркер для повторного запуска поверх изменённой базы. Откат миграции намеренно требует восстановления всей клиентской базы вместе с бизнес-данными. Набор загружается из встроенного JSON-ресурса; путь к нему или SQL нельзя передать из окружения. Новых публичных REST для заполнения нет.

## Проверки

Автоматические проверки `frontend/scripts/banking-demo.test.mjs` проверяют выключенное значение по умолчанию, уникальность и связи данных, шесть колонок, текущие/исторические оценки, формулу и простой, допустимость владельцев/исполнителей, уникальность активных слотов мер, пересмотры и согласованность относительных дат. Они проверяют шаблон набора, а не выполнение C#-транзакции на PostgreSQL.

Для приёмки запуска нужны отдельные проверки на тестовых БД:

1. False: число бизнес-записей до/после старта одинаково
2. True на новой базе: все 18 рисков доступны через API, доска содержит по 3 в колонке, карточка показывает процессы, владельцев, оценки, комментарии и меры
3. Повторный и параллельный старт: один маркер, неизменные количества и ID; изменённое в UI название и пароль не сбрасываются
4. Конфликт фиксированного demo-email/ID: после ошибки нет частично созданной оргструктуры или рисков, readiness клиента отрицательный
5. Два клиента: свои локальные роли и строки, JWT одного клиента не действует в другом; ошибка одного seed не открывает другую БД
6. Клиент с существующей шкалой и CEO: настройки/назначение сохранены; новые оценки согласованы с этими настройками
7. Необязательные демопароли: вход и права бизнес-роли, отсутствие пароля в ответах/логах; без параметра вход не создаётся
8. Переходы мер/пересмотр, текущий отчёт и исторический снимок после загрузки; журнальные задания обработаны штатным worker

HTTP-проверки отображения находятся в `Tests/Http/banking-demo.http`. Сборка, первый старт, миграция, повторный/параллельный запуск и загрузка на реальном PostgreSQL в этой работе не выполнялись: AGENTS.md запрещает сборки без отдельного запроса.
