# СУР. Поэтапный план реализации

## Целевая архитектура

Один модульный ASP.NET Core-бэкенд на основе текущего `IdentityApi`, один веб-клиент и **одна база PostgreSQL на клиента**. Один экземпляр приложения обслуживает несколько клиентов, каждый со своей бизнес-конфигурацией и данными. PostgreSQL, MinIO, SMTP и Jira остаются отдельными системами. Это целевое понимание распределённого монолита в этом плане. Распределение бизнес-модулей по отдельным процессам потребовало бы сетевых контрактов, согласования состояния и отдельных развёртываний.

Сохраняем четыре проекта `Api / Application / Domain / Infrastructure`, текущий Core и маршруты существующих контроллеров на этапе переименования. Внутри слоёв добавляем модули по функциональности:

| Модуль | Ответственность |
|---|---|
| Identity | Учётные записи, роли и права, выдача доступа, пароли, JWT и сессии |
| Оргструктура | Дирекции, сотрудники, процессы, владельцы, объекты и зоны ответственности |
| Управление рисками | Справочники, паспорт и связи риска, оценка, решения, меры, назначения, согласование, пересмотр, реестр и доска |
| История | Поручения и неизменяемые события бизнес-журнала, административная выборка |
| Интеграции и уведомления | Jira, обработка входящих уведомлений и доставка писем с доступом. Вебхук пересмотра остаётся в модуле рисков |
| Файлы и документы | Потоковое хранение и выдача через MinIO, формирование выгрузок. Состав среза и правила импорта принадлежат модулю рисков |

Модули вызывают прикладные операции внутри процесса. Создание пользователя с сотрудником, деактивация и отзыв ролей фиксируются в одной транзакции клиентской базы. Репозитории составной операции используют одно соединение и явно переданную транзакцию. Наличие одного scoped-подключения в текущем DI само по себе этого не обеспечивает. Для конкурентных изменений нужны ограничения в БД и проверка версии или сериализуемая транзакция с обработкой конфликта. В частности, назначение исполнителя или владельца и отключение пользователя должны участвовать в одном механизме контроля.

Для MVP предлагается сохранить Dapper и FluentMigrator. В новых записях применяем соглашения о физической модели из §24 проекта бэкенда, включая UUID-версии и обновление версии риска при изменении его дочерних данных. В Dapper условие по ожидаемой версии и её обновление выполняются в SQL; проверка отсутствия обходного пути входит в интеграционные тесты. Существующие таблицы Identity приводим к требованиям добавочными миграциями там, где это нужно для сценария. Массовое переименование таблиц и перенос на EF Core отдельной задачей в этот план не входят.

Защищённый запрос проверяет JWT, принадлежность клиенту, актуальную сессию и права по выбранной клиентской базе. Деловые ограничения проверяет профильный модуль. Внутренний RPC, брокер для связи модулей, саги между Identity и рисками и проекции прав для отдельных сервисов заменяются локальными вызовами и транзакциями. Состояние фоновых заданий остаётся в PostgreSQL, обработчики запускаются внутри хоста. Внешние SMTP, Jira и MinIO вызываются после фиксации локальных изменений. Для бизнес-журнала сохраняется установленный требованиями порядок через транзакционное поручение.

## Этап 0. Рабочий хост и границы клиентов

**Зависимости.** текущий `IdentityApi`.

- Переименовать каталог и решение в `SurPlatform`, обновить пути Dockerfile и название в Swagger. Отдельным изменением довести до согласованности вызовы JWT-хелпера и проверить конфигурацию DI. Сверить существующие маршруты, контракты, JWT issuer/audience и хранение RSA-ключей. Изменения поведения Identity вынести в этап 1.
- Заменить единственную строку `DefaultConnection` выбором клиентской базы через доверенный контекст. Предлагаемый вариант — зарегистрированный host клиента за nginx с явным соответствием конфигурации и проверкой привязки JWT к клиенту. Зафиксировать аналогичный выбор для webhook и фоновых заданий до обращения к данным. nginx передаёт только проверенный host, а приложение разрешает его по явному списку и фиксирует выбранную базу на весь запрос. Фоновые задания выбираются из клиентской базы и исполняются в её контексте. Клиентские бизнес-таблицы остаются без `tenantId`.
- Настроить Compose для бэкенда, веб-клиента, nginx и PostgreSQL. Подключать внешние зависимости на профильных этапах. Обеспечить создание отсутствующей клиентской базы, последовательное применение миграций и раздельный readiness баз. Запрос к клиенту с неподготовленной схемой отклоняется, ошибка подготовки не перенаправляет запрос в другую базу.
- Зафиксировать единый формат ошибок, правила версионирования HTTP, пагинацию, локальные транзакции и обработку устаревшей версии. Миграции для новой функциональности идут вместе с вертикальным срезом.

**Приёмка.** чистый и повторный старт, миграция существующей базы без потери записей, проверка входа и независимых сессий после переименования. Клиент A не может использовать свой JWT у клиента B даже при совпадающих идентификаторах пользователя и ресурса. Неизвестный host не открывает ни одну базу. §35, №70 и проект бэкенда §17–19, §22, §24.1–24.2.

## Этап 1. Вход, выдача доступа и административная ролевая модель

**Зависимости.** этап 0.

- Доработать имеющиеся JWT, сессии, хеширование и ротацию refresh. Установить короткий срок JWT, отдельные сроки сеанса и refresh, обновление версии прав и отзыв при выходе, смене пароля и повторном использовании старого refresh. Для браузера использовать refresh-cookie `HttpOnly/Secure` с CSRF-защитой и хранить access token в памяти. При согласовании контракта убрать неоднозначность двух действующих операций смены пароля.
- Реализовать идемпотентное заполнение шести системных ролей, каталога прав и исходной матрицы. Сделать вычисление эффективных прав и административный экран матрицы. Сохранить особые правила `admin`, запрет самоотключения и наличие хотя бы одного действующего администратора. Роли и права поставляются системным набором; изменения активности допустимых ролей и назначений прав применяются атомарно.
- Реализовать системную запись, начального администратора и служебную повторную выдачу. Добавить создание пользователя без оргданных, список и карточку, изменение ФИО и ролей активного пользователя, изменение email неактивного, активацию и сброс с повторной отправкой. Email уникален среди активных и неактивных. Для операций с организационными зависимостями применить ограничения этапа 2 и этапа 5 до открытия соответствующих сценариев пользователям.
- Настроить доставку первого и повторных писем: временный пароль действует 10 календарных дней и требует смены при первом входе; до смены закрыт обычный доступ. Сохранять версию выдачи и `PENDING/SENT/FAILED`; исходный пароль существует только в памяти отправки. Утрата секрета при сбое требует повторной выдачи. Запоздалый результат старой отправки не меняет состояние новой выдачи. Экран входа, смены пароля и администрирования довести до работы с этим API.

**Приёмка.** первый администратор получает доступ; повторный seed сохраняет уникальность; отказ SMTP оставляет учётную запись и понятный статус; устаревший пароль, токен или право не дают доступа. Два устройства работают независимо, конкурирующие refresh не создают два действующих продолжения. Источники 03, 05, §35, №1–5, 7–9, 69 и проект бэкенда §7, §14, §24.4.

## Этап 2. Оргструктура и составные операции с пользователями

**Зависимости.** этап 1. Интеграция с назначениями мер добавляется на этапе 5.

- Реализовать справочники дирекций, сотрудников, процессов и объектов, назначения CEO, директора и специалиста по оценке рисков. Учётная запись и сотрудник хранятся отдельно. Обеспечить одну активную запись сотрудника на пользователя, одного CEO на клиента и уникальность действующих назначений по правилам дирекции.
- Добавить административные операции создания, допустимого редактирования, активации и деактивации. Сохранять исторические связи. Перевод в другую дирекцию проводится через закрытие старой записи и создание новой. Замена владельца процесса после появления рисков обновляет действующие связи и добавляет системные комментарии в одной транзакции.
- В одной транзакции создавать пользователя, роли, сотрудника и выбранные начальные назначения; при конкурентном занятии позиции откатывать всё. Заменить физическое удаление пользователя деактивацией: проверить владение активными процессами и действующие назначения, деактивировать сотрудника и отозвать доступ. Активация учётной записи требует отдельной активации сотрудника по правилам оргструктуры.
- При отзыве ролей и деактивации ролей проверять затронутые организационные зависимости по всему набору пользователей. Действующие назначения мер и пригодность исполнителя включить в те же проверки на этапе 5.

**Приёмка.** конкурентные назначения одного ответственного не создают дублей; конфликт не оставляет частично созданного пользователя; деактивация и назначение не могут завершиться несовместимыми результатами. Источники 03–05, §35, №6, 10–13.

## Этап 3. Справочники, черновик риска, реестр и журнал

**Зависимости.** этап 2.

- Реализовать группы опасностей, опасности и категории с валидацией, уникальностью, активацией и деактивацией. Деактивированные записи видны в истории, но исключаются из выбора для новых связей.
- Реализовать паспорт черновика, основной процесс, необязательный объект, автора, допустимое редактирование, реестр и карточку. При создании обычный пользователь выбирает активный процесс своей дирекции; сервер проверяет право и организационный контекст. `view_risk` даёт просмотр всех рисков клиента. Поиск, фильтры, сортировка и пагинация выполняются в базе.
- Добавить комментарии и бизнес-журнал с первой изменяющей операции. Записывать поручение в транзакции команды, сохранять прежние и новые значения, участников, источник, время и общий идентификатор операции. Фоновая запись события идемпотентна по `eventId`; сбой сохраняет поручение для повтора. Системные комментарии неизменяемы, пользовательские удаляются логически по правилам авторства.
- Добавить канбан-представление на той же выборке с шестью статусами, счётчиками после фильтрации, переходом в карточку и состояниями загрузки, пустого результата и ошибки. Колонки заполняются по мере реализации переходов; канбан не изменяет состояние риска.
- Добавить административную историю и запрос на выгрузку по включительным датам UTC. Только администратор запускает выборку. Она объединяет записанные события и ещё не перенесённые поручения по `eventId` в одном согласованном снимке. Формирование JSON и выдача файла завершаются на этапе 8.

**Приёмка.** сохранение недоступно без права, деактивация справочника не ломает старый риск, ошибка сохранения поручения откатывает команду, повтор переноса не дублирует событие. Карточка отображается в одной колонке, без подстановки старой оценки. Источники 03, 06, 08, 15, 16, §35, №4, 14–15, 62–68.

## Этап 4. Оценка, шкалы и решение по риску

**Зависимости.** этап 3. Переходы, затрагивающие незавершённые меры и открытые пересмотры, завершаются на этапах 5–6.

- Реализовать один встроенный метод `R = L × I`, настройку полных денежных границ, неизменяемые версии шкалы и снимки исходных параметров. Сервер рассчитывает тяжесть по сумме или смешанному простою объекта. Неделя — 168 часов, день — 24 часа, округление до копеек по `HALF_UP` после умножения. Проверить нулевую оценку и граничные значения; нулевые веса сохраняются и не отображаются в цветовой матрице 5×5.
- Первую оценку и перевод черновика в «Активен» сохранять атомарно. Защитить единственность текущей оценки и запретить изменение паспорта после первой оценки. Технический пересчёт при изменении шкалы или стоимости часа обновляет применимый набор атомарно, создаёт новые версии и сохраняет выбранный способ работы. Принятые и закрытые риски сохраняют значения.
- Реализовать пороги принятия и уровни OWNER, DIRECTOR, CEO и TREATMENT_REQUIRED. Начальные границы 0–10, 11–15, 16–19 и 20–25. Применение новых порогов пересчитывает маршруты подходящих рисков без создания новой оценки.
- Реализовать выбор режима «Принять», «Обработать», «Разделить» и «Передать», а также закрытие. Проверять актуальные права, уровень и владельца нужного процесса. Один способ на цикл. Разделение сохраняет одну карточку и один основной процесс. Передача сохраняет прежние связи и запускает пересмотр через команду этапа 6. Принимать или закрывать при наличии только черновых мер можно по профильным правилам; перед передачей черновики также подлежат отмене.

**Приёмка.** две конкурентные первые оценки дают одну текущую версию; ошибка одной строки пакетного пересчёта оставляет прежнюю шкалу и оценки; изменение порогов не подменяет историю; после первого расчёта паспорт защищён даже для администратора. Источники 07–10, §35, №16–31, 47.

## Этап 5. Меры, согласования и ручное исполнение

**Зависимости.** этап 4. Транзакцию запуска риска подготовить для подключения Jira на этапе 7, завершение последней меры связать с этапом 6.

- Реализовать карточку меры с привязкой к процессу риска, сроком, плановой и необязательной фактической стоимостью, комментариями и явными командами переходов. В черновике мера без исполнителя и задачи Jira; после выхода из черновика деловые сведения защищены. Для одной пары «риск — процесс» через текущие и исторические связи допускается одна мера в статусах «На согласовании», «Согласовано», «Ожидает выполнения» или «В работе». Холд не занимает это место.
- Настроить маршруты согласования по плановой стоимости и снимок сработавшего правила. Начальные пороги 0, 50 000 и 100 000. Проверять наличие действующего согласующего. Сохранять не более одного ожидающего запроса. Добавить очередь «На согласование» со счётчиком, решение, отклонение с причиной и административный отзыв с сохранением истории.
- Назначать одного активного сотрудника дирекции процесса с подходящей действующей ролью OWNER или EMPLOYEE. Назначение и переход в «Ожидает выполнения» фиксируются вместе. Замена и снятие выполняются по текущему статусу и режиму управления. Добавить проверки исполнителей к деактивации и отзыву ролей этапа 2.
- Общий запуск риска переводит весь ожидающий набор мер в «В работе» одной транзакцией. Добавить ручной холд, возобновление, завершение и отмену по статусной модели. Завершение последней активной меры должно фиксировать пересмотр в той же транзакции после этапа 6, включая требуемое подтверждение при оставшихся черновиках.

**Приёмка.** конкурентные меры и решения согласования соблюдают ограничения, запуск не оставляет частично переведённый набор, исполнитель не получает право на изменение только из факта назначения. Источники 11–13, 16, §35, №32–42, 45–47, 61.

## Этап 6. Пересмотр и полный ручной цикл

**Зависимости.** этапы 4–5. Реализовать транзакционный вход в пересмотр прежде, чем включить передачу риска и завершение последней меры.

- Реализовать `ReviewRun` и `RiskReview` для четырёх оснований. Передача — ручной пересмотр с источником `TRANSFER`. Успешный запуск историзирует оценку, очищает текущий уровень принятия и переводит риск в «Ожидает переоценки». Подтверждённый ручной возврат закрытого риска очищает причину закрытия и пишет системный комментарий.
- Настроить несколько расписаний и вебхуков, ответственных, сохранение снимков настроек и календарной зоны. Расписания обрабатывают актуальную выборку принятых рисков, поддерживают календарные повторы и последний день короткого месяца. Уникальный ключ срабатывания предотвращает дубль; пустая выборка тоже фиксируется.
- Вебхук пересмотра принимает запрос по HTTPS с отдельным Bearer-секретом, поддерживает смену токена, сохраняет исходное тело после авторизации и получает набор рисков из настройки. Повторный HTTP-приём создаёт новый запуск; повтор обработки сохранённого запуска не дублирует результат. Для каждого риска отдельная транзакция и результат `WAITING/NO_ACTION/ERROR`; открытый пересмотр может быть только один.
- Завершать пересмотр человеческой переоценкой или закрытием. Переоценка создаёт новую текущую оценку, переводит риск в «Активен» и открывает новый цикл выбора способа работы. В карточке показать причину, ответственного, автора настройки и историю завершённых пересмотров.

**Приёмка.** сквозной ручной сценарий «черновик → оценка → меры → пересмотр → новая оценка или закрытие», включая конкурентное завершение последних мер и сбой одной записи массового запуска. Автоматический запуск не создаёт оценку за пользователя. Источники 08–11, 14, 16, §35, №31, 45–54.

## Этап 7. Jira Data Center

**Зависимости.** этапы 5–6, фоновые задания этапа 3.

- Реализовать одно подключение на клиента: защищённые реквизиты, проект, тип задачи, ответственный, проверка обязательных полей, соответствие исполнителей и статусов. Срок передавать как календарную дату по сохранённой зоне. Настройки и журнал ошибок доступны администратору.
- При запуске риска и предусмотренном возобновлении меры сохранять поручение создания вместе с изменением статуса. Обработчик применяет повторы до достоверной отправки; после неизвестного результата переводит поручение в состояние для ручной проверки. Администратор связывает найденную задачу после проверки или явно подтверждает её отсутствие. Сохранить уникальность связи в обе стороны.
- Принимать webhook Jira по HTTPS с отдельным Basic-секретом, подтверждать приём после сохранения и перечитывать задачу через REST. Применять статус и исполнителя через те же проверки предметного модуля. Защитить от запоздавших событий и повторной обработки. Фиксировать источник, системного исполнителя, ответственного и автора настройки.
- Реализовать переключение ручного и внешнего управления, восстановление при повторном включении и исключение для «Холд» без задачи и без неопределённой попытки. Отправка в процессе отключения сохраняет свой результат, завершённая мера не открывается. Показывать пользователю ожидание, подтверждённую ссылку или неопределённый итог и доступные действия.

**Приёмка.** сбой после начала POST не порождает второй POST; повтор webhook не дублирует применение; терминальные меры остаются закрытыми; штатное изменение статуса видимо в карточке в пределах 60 секунд. Источник 17, §35, №42–44, 55–60 и проект бэкенда §11.

## Этап 8. Файлы, отчёты, импорт и справка

**Зависимости.** рабочий реестр, журнал и предметные сценарии этапов 3–6. С этапа 2 команды, меняющие отображаемые в отчётах данные, сохраняют их исторические версии в той же транзакции. К этапу 8 есть исходные сведения для срезов на прошлую дату.

- Реализовать файловый модуль с потоковой передачей в MinIO, подтверждением размера и контрольной суммы, устойчивым ключом загрузки и `fileId`. Привязывать операции и объект к клиенту; проверять право на скачивание при каждом запросе. Восстанавливать результат после сбоя между записью объекта и фиксацией метаданных.
- Реализовать отчётные права, выбор параметров, согласованные снимки и фоновые задания. Срез объединяет риски, оценки и меры, содержит автора и время среза и формирования. Историческая выгрузка берёт значения на дату среза из сохранённых версий. CSV/Excel защищены от формул из пользовательских строк. JSON административной истории доступен только администратору; поддерживается пустой результат. PDF и тепловая карта зависят от отдельного решения по объёму.
- Реализовать импорт реестра рисков из CSV: загрузка, сопоставление столбцов, проверка и обработка ограниченными порциями, отчёт по строкам. Валидные строки проходят правила создания риска; повтор задания или строки не создаёт дубликат. Отдельный импорт мер зависит от согласования.
- Завершить экраны отчётов, импорта, административной выгрузки, справку и глоссарий. Для длительных операций показать состояние, ошибку и допустимый повтор. Генерация и импорт используют сохранённое задание, а повтор команды с тем же ключом возвращает прежний результат.

**Приёмка.** изменение справочника после выбранного момента не меняет исторический отчёт; пользователь без права не получает файл даже по известному идентификатору; повтор после сохранения файла и потери ответа возвращает тот же результат. Источники 00–01, 16, сводное описание §18.4, §35, №66, 69–70, проект бэкенда §12–13, §24.7–24.8.

## Этап 9. Готовность к выпуску

**Зависимости.** все функциональные этапы.

- Пройти профильные критерии 03–17 и сводные №1–70. Проверить сквозные сценарии входа и выдачи, деактивации, риска и согласования, обеих схем исполнения, календарного и webhook-пересмотра, импорта и выгрузок. Для конкурентности и откатов использовать реальный PostgreSQL; для внешних границ — тестовые Jira, SMTP и MinIO.
- Проверить изоляцию двух клиентских баз на HTTP, JWT, webhook, заданиях, файлах, истории и отчётах. Проверить ошибки прав после открытия формы, отсутствие секретов в логах, ответах и выгрузках, ограничения размеров, таймауты и доступность только нужных маршрутов nginx.
- Измерить полный путь ключевых экранов: `p95 ≤ 1 с`, для Jira — штатное отражение изменения за 60 секунд. Ограничить параллельность фоновых задач, проверить планы SQL, конкуренцию отчётов и импорта с обычными запросами. Фиксировать время и ошибки HTTP, возраст заданий, конфликты PostgreSQL, задержку Jira, состояние импорта и отправки.
- Проверить запуск пустого окружения, повторный запуск, обновление схемы клиентских баз и восстановление PostgreSQL, файлов и ключей в отдельной среде. Перед возобновлением внешних отправок сверить задания и связи Jira. Описать установку, создание первого администратора и восстановление для сдачи MVP.

**Приёмка.** пройдены сквозные сценарии и восстановление, результаты нагрузочных и изоляционных проверок воспроизводимы. Источники 01 §3, сводное описание §22, §35 и проект бэкенда §20–22.

## Решения к началу затронутых этапов

| Когда | Решение и влияние |
|---|---|
| Этап 0 | Подтвердить предложенный выбор клиента по доверенному host, привязку токенов, маршрутизацию webhook и порядок подключения новых клиентских баз. Утвердить Dapper/FluentMigrator как адаптацию EF Core из проекта бэкенда |
| Этапы 0–1 | Согласовать конечные публичные маршруты. Предложение для MVP — использовать имеющееся соглашение `public/provider/internal`, фиксировать новые контракты в OpenAPI по мере реализации. Согласовать отображение текущего GUID `ManageUsers` на системное право `admin` и переход браузерного контракта |
| Этап 7 | Сверить доступность реального Jira Data Center, схему входящего Basic и поля создания. Для штатного обмена действует профильный критерий 60 секунд; упоминание суточной синхронизации в общей постановке требует уточнения как отдельный механизм сверки |
| Этап 8 | Подтвердить PDF, тепловую карту в отчётах и импорт мер. PDF указан в общей постановке, серверный проект описывает CSV/Excel/JSON. Тепловая карта отчётности отличается от обязательной матрицы оценки. Импорт реестра подтверждён, отдельный импорт мер указан в декомпозиции |
| Этап 9 | Зафиксировать объём тестовых данных и профиль нагрузки, параметры резервирования, целевые потери данных и время восстановления. Источники задают целевые показатели продукта, параметры конкретной среды требуют согласования |

Отдельный модуль мониторинга рисков с алертами, плагины методик и отдельная история записей назначения исполнителя исключены из MVP по профильным разделам. Бизнес-журнал изменений назначений и автоматический пересмотр входят в объём. Первое рабочее демо — после этапа 6. Полный MVP по подтверждённому объёму — после этапов 7–9.
