# Оргструктура СУР

Административные операции доступны под `/api/v1/provider`. Для них требуется действующая административная сессия в базе клиента, выбранного по HTTPS-хосту.

| Метод и путь относительно префикса | Результат |
| --- | --- |
| `GET /organization/{directory}`, `GET /organization/{directory}/{id}` | Страница и карточка. Справочники: `directorates`, `persons`, `processes`, `assets`, `responsibilities` |
| `POST /organization/{directory}` | Создание записи или замена назначения, ответ 201 |
| `PUT /organization/{directory}/{id}` | Редактирование дирекции, сотрудника, процесса или объекта. Для дирекции и объекта `version` передаётся в query, для сотрудника и процесса — в JSON |
| `PUT /organization/{directory}/{id}/state` | Изменение состояния с `version` и `isActive`. Назначение можно только завершить |
| `GET /organization/responsibilities/slot` | Состояние позиции по `responsibilityType` и, кроме CEO, `directorateId`. Ответ содержит `assignmentId` и `observedAt` |
| `PUT /organization/processes/{id}/owner` | Подтверждённая замена владельца с `version`, `ownerId` и `confirmed: true` |
| `GET /users/{id}/organization` | Активный сотрудник, его процессы и назначения для подтверждения деактивации |
| `POST /users` | Создание учётной записи с ролями и необязательным объектом `organization` |
| `POST /users/{id}/deactivate` | Деактивация по версии пользователя, ответ содержит обновлённую карточку |
| `POST /users/{id}/activate` | Активация учётной записи с отдельной последующей активацией сотрудника |

Списки поддерживают `after`, `limit`, `active`, `search`. Для сотрудников, процессов и назначений доступен `directorateId`. Историю CEO, директора и специалиста можно фильтровать по точному `responsibilityType`. Курсор — ID последней строки полученной страницы. Поля DTO и типы ответов описываются контроллерами в OpenAPI.

При составном создании `organization` содержит `directorateId`, `positionName` и `responsibilities`. Каждый элемент `responsibilities` содержит `responsibilityType`, `directorateId` для локальной ответственности и `observedAt` из запроса состояния позиции. Если назначение существовало на момент наблюдения, сервер вернёт `RESPONSIBILITY_SLOT_OCCUPIED`. Если оно появилось после наблюдения, сервер вернёт `RESPONSIBILITY_SLOT_CHANGED`. Оба ответа имеют статус 409. Момент наблюдения используется для объяснения конфликта. Свобода позиции определяется состоянием базы внутри транзакции.

При замене назначения передайте `previousId` и `previousVersion`. Старая запись завершится в той же транзакции, в которой появится новая. Для CEO можно выбрать активную запись сотрудника через `personId` или указать `userId`. Во втором случае система использует имеющегося активного сотрудника либо создаёт его без дирекции. При повторной активации конкретного сотрудника без дирекции укажите `assignCeo: true` в команде изменения состояния.

Перевод сотрудника состоит из деактивации прежней записи и создания новой записи с тем же `userId` и целевой дирекцией. После отдельной активации учётной записи можно активировать выбранную прежнюю запись сотрудника по её ID. Активное владение процессом или назначение блокируют деактивацию. В ответе 409 `ORGANIZATION_DEPENDENCIES` передаются `dependencyIds`. Физическое удаление по прежнему `DELETE /users/{id}` возвращает 410.

Миграция `202611140200` добавляет справочники, ограничения уникальности действующих назначений и JSON-снимки `OrgHistoryDal`. Снимок записывается с каждой сохранённой версией оргзаписи. Составное создание, замена назначения, деактивация и отзыв ролей используют общий клиентский `pg_advisory_xact_lock` и одну транзакцию. Письмо отправляется после коммита.

Смена владельца сохраняет процесс и его снимок. На этапе 3, когда появятся модели рисков, в эту же команду нужно включить обновление всех действующих связей процесса, обновление версий затронутых рисков и создание одного системного комментария на риск. Проверки назначений мер подключаются на этапе 5. Пересчёт оценок после изменения стоимости простоя требует модели оценок.

Ручные сценарии находятся в `backend/Apps/SurPlatform/Tests/Http/organization.http`. Для параллельного теста одновременно отправьте два запроса составного создания CEO с разными email и одним `observedAt`. Ожидаются 201 и 409. Проверьте через список пользователей и сотрудников, что проигравшая запись отсутствует. Для гонки назначения и деактивации отправьте одновременно команды назначения и деактивации одного активного сотрудника. После коммита либо назначение действует и деактивация отклонена, либо сотрудник отключён и назначение отклонено.
