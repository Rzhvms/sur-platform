## Что изменено

Публичный GET `/health/release` возвращает только версии и имеет `Cache-Control: no-store`. Проверка зарегистрированного клиента остаётся на стороне хоста. Данные БД, миграции и транзакционные границы не менялись. HTTP-инфраструктурный контроллер читает конфигурацию и не вызывает репозитории.

SPA проверяет версию контракта перед показом рабочих форм. В development достаточно совместимого API; в production дополнительно сверяется точная пара версии/ревизии API с `/release.json`. Манифест фиксирует версию SPA, git-ревизию, признак dirty, пару API и SHA-256 проверенного OpenAPI. Хеш является отметкой проверенной схемы, а не автоматическим сравнением с живой схемой. При несовпадении или ошибке показаны отдельные сообщения, повтор проверки и обновление страницы. Деморежим доступен без API и явно подписан.

Dev-proxy пропускает точный `/health/release` и только публичные/административные группы API, очищает forwarding-заголовки и проверяет upstream TLS. Служебные API и неоднозначные пути не проксируются.

Nginx обслуживает статическую SPA, не кэширует API и не перехватывает его ошибки; глубокие ссылки используют `index.html`, отсутствующие JS/CSS возвращают 404. Заголовки безопасности заданы на уровне server, чтобы location для index не отменял наследование. CSP запрещает сторонние источники и выполнение inline-скриптов/eval. `style-src 'self' 'unsafe-inline'` пока необходим для стилей Angular; это осознанное ограничение текущей политики. Production-оптимизация отключает inline critical CSS и внешнюю загрузку шрифтов. Реальную совместимость CSP необходимо подтвердить на production-сборке, одной проверки конфигурации недостаточно.

Журнал nginx исключает query string, тела и заголовки. Необработанное исключение bootstrap заменено общим сообщением. Манифест содержит только публичные метаданные. JWT, cookie и секреты не входят в замеры навигации.

## Два клиента за nginx

Нужны два разрешённых HTTPS-host, две отдельные подготовленные базы, доверенный сертификат nginx и статический production-каталог. В обеих базах создать риск с одинаковым ID и разными названиями; использовать отдельные тестовые учётные записи. Сначала проверить собственные данные, затем JWT A на B и наоборот. Проверить отсутствие чужих cookie, BroadcastChannel-событий, состояния фильтров/кэша и рабочих URL. Выход в одном клиенте не должен завершить сессию другого. Отдельно изменить Host/forwarded-заголовки и проверить отказ неизвестному host без выбора резервной БД.

Read-only сценарий `frontend/tests/release/check-hosts.mjs` проверяет deep link и заголовки, отсутствие SPA fallback для API, закрытые internal-маршруты, пару версий и авторизованную изоляцию по одинаковому ID. Он не подтверждает изоляцию браузерных cookie/кэша и бизнес-записей. Без двух тестовых токенов и общего ID завершается неуспехом, а не пропускает приёмку молча. Пример запуска приведён в frontend/README.md. На текущем localhost-стенде сценарий двух клиентов не выполнялся.

Для приёмки сначала зафиксировать браузер, машину, размеры баз, параллельность, сеть, cold/warm cache и число повторов; затем собрать отдельные выборки для реестра, доски, карточки и вычислить p95. Цель ≤1 с из документа 01 пока **не измерена** на согласованной нагрузке. Единичный быстрый ответ curl не является результатом этого измерения.

Для Jira измерить от UTC-времени штатного изменения тестовой задачи до отрисовки в уже открытой карточке с учётом webhook/worker и интервала frontend polling. Цель ≤60 с пока **не подтверждена**. Упоминание суточной синхронизации в старом документе 01 расходится со специализированным 17 и заданием этапа: для приёмки применяем явную цель 60 с, расхождение источников требуется устранить в документации продукта.

## Подготовка маркированной сборки

Эти команды являются инструкцией, в текущей работе сборка не выполнялась. Сначала определить реальную версию и git-ревизию собранного API, задать ему `Release__Version` и `Release__Revision`, перезапустить и сверить `/health/release`. `unrecorded` не подходит для принятого выпуска. После проверки OpenAPI сохранить его точные байты в артефакты кандидата.

```sh
cd frontend
SUR_RELEASE_API_VERSION=0.1.0 \
SUR_RELEASE_API_REVISION=actual-api-commit \
SUR_RELEASE_OPENAPI=/absolute/path/to/reviewed-openapi.json \
npm run build:release
```

`build:release` сначала пишет публичный манифест, затем выполняет production-сборку. При отсутствии параметров маркировки операция завершается ошибкой. Проверить, что манифест совпадает с развёрнутым API, признак dirty=false и файлы `index.html` и `release.json` обновлены вместе с hashed JS. Развернуть готовый статический каталог через существующий compose override с `--no-build`; инструкция — в frontend/README.md. После этого проверить CSP в реальном браузере, fallback, ошибки API и два host. Хранить манифест, точный OpenAPI и результаты приёмки вместе с артефактом выпуска. Откат выполнять согласованной парой API/SPA.
