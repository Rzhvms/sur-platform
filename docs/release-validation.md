## Нагрузка

Базовый профиль использовал по одному риску на клиента, PostgreSQL 16 и прямой HTTPS Kestrel. По 5 прогревочных и 60 измеряемых обращений на маршрут, 4 одновременно. Измерение включает TLS, получение всего ответа, JWT и базу. В нагрузку не входили браузер, nginx, параллельный импорт и генерация файлов.

| Маршрут | p95 в первом прогоне | p95 во втором | p95 после добавления сценария перезапуска | Ошибки |
| --- | ---: | ---: | ---: | ---: |
| Реестр рисков | 92,9 мс | 177,2 мс | 77,6 мс | 0 |
| Доска | 65,5 мс | 80,6 мс | 75,3 мс | 0 |
| Карточка риска | 61,8 мс | 113 мс | 71,5 мс | 0 |

Для выпуска зафиксируйте согласованные объёмы, оборудование, число клиентов, параллельность и набор фильтров. Запустите сначала базовую серию, затем тот же профиль во время импорта и генерации отчёта. Сравните задержки и ошибки по каждому маршруту. Цель p95 API — не выше 1 с. Полный пользовательский путь измеряется отдельно в браузере через nginx.

```sh
python3 backend/Apps/SurPlatform/Tests/Release/probe.py \
  --base https://alpha.sur.test --peer https://beta.sur.test --risk-id "$RISK_ID" \
  --endpoint '/api/v1/public/risks?limit=30' \
  --endpoint '/api/v1/public/risks/board?limit=30' \
  --endpoint "/api/v1/public/risks/$RISK_ID" --samples 60 --concurrency 4
```

Передайте тестовые токены в окружении `SUR_TEST_TOKEN` и `SUR_TEST_PEER_TOKEN`. У обоих клиентов создайте риск с тем же ID и разными названиями. Для локального сертификата передайте доверенный PEM через `SSL_CERT_FILE`.

Для SQL получите планы фактических запросов реестра, доски и отчётного снимка на восстановленной копии с сопоставимым распределением. Выполните `EXPLAIN (ANALYZE, BUFFERS)` для чтения и для материализации снимка внутри транзакции с `ROLLBACK`. Сравните число строк до и после фильтров, сортировки, буферы и оценки планировщика. Проверьте блокировки при одновременной оценке, назначении и деактивации. Запишите план и фактический результат для каждой проверки.

Команда `docker compose --profile documents config --quiet` с тестовыми переменными завершилась успешно. C# и SQL прошли статические проверки, `git diff --check` прошёл.

## Jira, SMTP и файлы

- Jira. Начните с известного состояния связанной меры. Зафиксируйте момент изменения тестовой задачи в UTC и измерьте задержку командой ниже. Для неизвестного POST потеряйте ответ после фактического создания и проверьте, что второй POST отсутствует до ручного решения. Проверьте реакцию на просроченный webhook и сигнал с данными другого клиента.
- SMTP. Используйте тестовый сервер с STARTTLS. Проверьте доставку, отказ и повторную выдачу, затем выполните поиск фиктивного секрета в логах и выгрузках. В протокол сохраняйте счётчик совпадений, не пароль.
- MinIO. Проверьте успешные CSV/XLSX/JSON, ошибку SHA-256, доступ к файлу после отзыва прав и восстановления, повтор после падения между PUT и фиксацией результата, два клиента с одним бакетом. Запросы хранит `Tests/Http/documents.http`.
- nginx. Через каждый HTTPS-хост проверьте readiness, отклонение чужого Host/SNI, ошибку `413` за пределом размера загрузки и недоступность `/api/v1/internal/…`.
- Остановка. На тестовом кандидате прервите импорт после нескольких записей и перезапустите хост. Успешные строки должны остаться в одном экземпляре. Повторите для передачи журнала и восстановления незавершённого отчёта.
- Контроль секретов. Используйте одноразовые контрольные значения для JWT, refresh-cookie, Jira PAT и SMTP-пароля. Проверьте тело ошибок, stderr/stdout, nginx access log и административный JSON. В отчёте сохраняйте только факт совпадения.

```sh
python3 backend/Apps/SurPlatform/Tests/Release/probe.py \
  --base https://alpha.sur.test --jira-treatment-id "$TREATMENT_ID" \
  --jira-status "$EXPECTED_SUR_STATE" --jira-changed-at "$JIRA_CHANGED_AT"
```

`JIRA_CHANGED_AT` передаётся в ISO 8601 со смещением. Сценарий завершится с ошибкой, если целевой статус не виден за 60 с. Перед изменением убедитесь, что мера находится в другом состоянии.

Открытые параметры выпуска — объём и распределение тестового набора, профиль нагрузки, RPO и RTO. Их фактическое подтверждение требует согласованного стенда. Доступность внешних адаптеров, полное восстановление и сквозные критерии не засчитываются по этому базовому прогону.
