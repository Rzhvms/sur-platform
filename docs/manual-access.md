# Ручная выдача доступа без почты

Решение пользователя от 2026-11-26 заменяет прежний почтовый сценарий целиком. Подключение почтового транспорта, отправщики, их порт, DI и переменные Compose удалены. Новые учётные записи создаёт администратор клиента через `/admin/users/new` или provider API.

## Пользовательский сценарий

1. Администратор задаёт ФИО, уникальный email, активные роли, при необходимости оргданные и временный пароль с подтверждением
2. Создание пользователя, ролей, оргданных и хеша пароля выполняется одной транзакцией; конфликт позиции откатывает всё
3. Администратор самостоятельно передаёт пароль получателю. Ответ API не возвращает пароль
4. Вход временным паролем открывает только смену пароля. До неё обычные API запрещены. Срок — 10 календарных дней с момента выдачи
5. Пользователь меняет пароль через существующий PATCH `/api/v1/public/users/change-password`, затем входит заново
6. При потере доступа администратор открывает карточку и выбирает повторную выдачу. Новый временный пароль заменяет прежний; старые сессии отзываются. Операция требует актуальной версии карточки

Активация неактивной учётной записи также требует нового временного пароля. Активация сотрудника остаётся отдельной организационной операцией. Роль сама не создаёт назначение. Для проверки каждой бизнес-роли необходимо назначить права и нужные оргсвязи; добавление ADMIN в тестовую учётную запись скрывает ошибки разграничения.

## HTTP-контракт

Все три команды доступны только администратору с действующей сессией текущего клиента. Передавайте Bearer в Authorization. Пароль передаётся только в JSON по HTTPS, не в URL и не в query string.

- `POST /api/v1/provider/users`: существующие поля `email`, `fullName`, `roleIds`, `organization` плюс обязательный `temporaryPassword`
- `POST /api/v1/provider/users/{id}/activate`: `version`, необязательный `roleIds`, обязательный `temporaryPassword`
- `POST /api/v1/provider/users/{id}/reissue-access`: JSON `{ "version": "<прочитанная версия>", "temporaryPassword": "<новый временный пароль>" }`. Версия перенесена из query в JSON

`temporaryPassword`: обязательная непустая строка 8–256 символов; пробелы по краям не удаляются. Подтверждение проверяется фронтендом, в API передаётся одно значение. Ошибки модели дают 400; дополнительная проверка сервиса возвращает 400 с кодом `INVALID_TEMPORARY_PASSWORD`. Устаревшая версия даёт 409. Маршруты сохранены; старые запросы без пароля больше не выполняют выдачу и требуют обновления клиента.

DTO имеют ограничения длины для OpenAPI; общий schema filter помечает temporaryPassword как format=password и writeOnly. Исходный пароль отсутствует в модели ответа и исключён из ToString запросов. Обновлённый Swagger надо получить после пересборки API; сохранённый `openapi/stage07-local.json` отражает предыдущую запущенную сборку и не подтверждает этот контракт.

## База и совместимость

Новые миграции не нужны. Используются существующие credential/profile/session-таблицы и ограничения. Исходный пароль хешируется существующим механизмом с независимой солью. Запись хеша, срока, признака обязательной смены, версии прав и отзыв сессий выполняются одной локальной транзакцией.

Колонки прежних статусов и версий выдачи сохранены для существующих баз и исторических записей. При новой выдаче их значения очищаются. Поле `invitationStatus` сохранено в ответе для совместимости, новая выдача возвращает null. Фронтенд больше не трактует старый статус доставки как доступность учётной записи. Пользователь со старой неудачной выдачей получает доступ через повторную выдачу нового пароля.

Первый локальный администратор по-прежнему настраивается через `Clients[..].FirstAdministrator.DevelopmentPassword` только в Development. Повторный обычный старт не сбрасывает его пароль. Это отдельный исходный механизм, не общий пароль для пользователей.
