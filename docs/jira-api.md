# Jira Data Center

| Метод и путь после `/api/v1` | Назначение |
| --- | --- |
| `GET /provider/jira` | Текущая настройка или `204` |
| `POST /provider/jira/metadata` | Проекты или типы задач и статусы выбранного проекта |
| `PUT /provider/jira` | Сохранение настройки с `version`, включение и отключение |
| `GET /provider/jira/errors` | Журнал с `offset` и `limit` |
| `POST /provider/jira/treatments/{id}/resolve` | Для `UNKNOWN` передать `attemptStartedAt` из карточки и указать найденную задачу в `issue` либо подтвердить её отсутствие через `confirmAbsent` |
| `POST /public/jira/webhook` | HTTPS, Basic `jira:<webhookSecret>`, JSON с `issue.id`, ответ `202` после записи сигнала |
| `GET /public/treatments/{id}` | Поле `jira` со статусом доставки, подтверждённым ключом и ссылкой, признаком ручного управления |

Оператор задаёт точные HTTPS URL с контекстным путём через `Jira__AllowedBaseUrls__0`, `Jira__AllowedBaseUrls__1` и далее. REST использует отдельный Jira PAT. Хранилище ключей ASP.NET Data Protection должно сохраняться между перезапусками. Пароль вебхука передаётся отдельно, для настройки используйте случайный секрет длиной от 24 до 256 символов. Для первого сохранения `version` равна пустому UUID. При смене базового URL требуется новый PAT. После появления связей или неопределённых попыток адрес, проект и тип блокируются, чтобы не сверять существующие задачи в другой Jira.

Локальное соответствие принимается и возвращается в `executors` как словарь «ID учётной записи СУР → логин Jira». При включении оно сверяется с рабочим email и доступностью назначения в проекте. Требуются права просмотра, создания и назначения. Если Jira требует описание при создании, оно должно иметь значение по умолчанию: у меры в СУР описание необязательно. Дата меры уже хранится как календарная дата в клиентской зоне. В Jira передаётся то же число в формате ISO без сдвига суток.

После коммита запуска работник выполняет предварительную проверку задачи и записывает `SENDING` перед POST. Сбой предварительной проверки допускает повтор. Если после начала POST задача не подтверждена, попытка переходит в `UNKNOWN`, в том числе при HTTP-ошибке. При аварийной остановке незавершённая попытка становится `UNKNOWN` после двух минут. Отключение останавливает новые попытки, сохраняя уже полученный результат отправки. Подтверждённые задачи перечитываются при сигналах и периодически. Смена статуса, исполнителя и пересмотр после последней меры фиксируются вместе.

REST-контракт основан на [Jira Data Center REST API 10.3](https://developer.atlassian.com/server/jira/platform/rest/v10003/api-group-issue/).

## Проверка на тестовом экземпляре Jira

- После запуска риска сравните время и состав поручений с изменениями мер. Откат локальной транзакции должен убрать и поручения, и переходы.
- Смоделируйте сбой проверки исполнителя перед POST, создание с потерянным ответом, ошибку записи подтверждённой связи и отключение во время запроса. Сверьте фактическое число POST и запись ошибки. Повтор после неопределённого результата допустим только после явного подтверждения отсутствия задачи. Проверьте этот сценарий и для прокси, который после создания задачи подменяет ответ кодом `429`.
- Для связанной меры отправьте webhook с подменённым статусом, затем повторите события в обратном порядке. Мера должна следовать результатам GET Jira. Сравните даты наблюдений, количество изменений журнала и время обновления карточки. Отправьте второй сигнал во время GET и проверьте, что завершение первого чтения сохранило второй сигнал.
- Проверьте повторное включение для терминальной меры, «В работе» и «Холда» без задачи. Для «Холда» возобновление создаёт поручение. Терминальная мера может дать запись о расхождении и остаётся терминальной.
- Проверьте дату, заданную на границе суток в клиентской зоне, и измерьте время отражения изменений под типичной нагрузкой клиента.
