# Запуск бэкенда СУР

`SurPlatform` запускается одним ASP.NET Core-хостом. Для каждого клиента настройка `Clients__N__Host` задаёт каноническое DNS-имя, `Clients__N__ConnectionString` задаёт отдельную базу. Приложение принимает HTTPS-запросы для зарегистрированных имён. nginx проверяет совпадение TLS SNI с HTTP Host, передаёт канонический Host и заменяет X-Forwarded-Proto. ASP.NET Core учитывает только X-Forwarded-Proto от `Http__KnownProxy`. При прямом запуске используйте HTTPS Kestrel. Порты приложения и PostgreSQL из Compose наружу не публикуются.

## Подключения PostgreSQL

В `Apps/SurPlatform/Api/appsettings.json` задан пример для заранее созданной локальной базы и HTTPS-профиля с хостом `localhost`. Переопределите его в `Apps/SurPlatform/Api/appsettings.Development.json` при `ASPNETCORE_ENVIRONMENT=Development` или через переменные окружения.

```json
{
  "Clients": [
    {
      "Host": "localhost",
      "ConnectionString": "Host=127.0.0.1;Port=5432;Database=sur_local;Username=sur_local;Password=CHANGE_ME"
    }
  ]
}
```

Замените `CHANGE_ME` паролем роли PostgreSQL в локальном файле или передайте полную строку через окружение. Переменные окружения переопределяют одноимённые значения из JSON. Для первого клиента используются:

| Переменная | Назначение |
| --- | --- |
| `Clients__0__Host` | Каноническое имя клиентского HTTPS-хоста |
| `Clients__0__ConnectionString` | Рабочая строка подключения. Если PostgreSQL требует пароль, передайте здесь полную строку с `Password` |
| `Clients__0__MigrationConnectionString` | Подключение для миграций. По умолчанию используется рабочая строка |
| `Clients__0__BootstrapConnectionString` | Подключение к служебной базе для создания отсутствующей клиентской базы. Для заранее созданной базы поле можно опустить |

Для следующих клиентов используйте индексы `1`, `2` и далее. Пароли и реальные строки подключения храните в окружении или в локальном файле конфигурации, исключённом из Git.

## Локальный Compose

При прямом локальном запуске с профилем `https` интерфейс Swagger доступен по `https://localhost:7224/swagger`. Запросы на локальный HTTP-порт 5248 перенаправляются на HTTPS-порт 7224. Swagger UI и его OpenAPI-документы доступны в Development до проверки клиентской базы. Для вызовов API через Swagger используйте HTTPS-хост, указанный в `Clients`, с подготовленной базой.

- Для `alpha.sur.test` и `beta.sur.test` подготовьте локальное разрешение имён на 127.0.0.1 и сертификат с обоими именами в SAN. Укажите абсолютный путь `SUR_TLS_DIR` к каталогу с `tls.crt` и `tls.key`.
- Задайте `SUR_POSTGRES_PASSWORD`, `SUR_BOOTSTRAP_PASSWORD`, `SUR_ALPHA_PASSWORD`, `SUR_BETA_PASSWORD` в окружении оболочки через `export`. Для локальной конфигурации используйте уникальные случайные буквенно-цифровые пароли. Compose передаёт готовые строки Npgsql в приложение через те же переменные `Clients__N__…`.
- Из каталога `backend` выполните `docker compose up -d postgres`. Для нового тома один раз создайте роли командой ниже. Для существующего тома проверьте, что роли и пароли соответствуют окружению.
- Запустите приложение и nginx командой `docker compose up --build`. `SUR_ENVIRONMENT=Development` включает Swagger по `/swagger`.

```sh
docker compose exec -T \
  -e SUR_BOOTSTRAP_PASSWORD -e SUR_ALPHA_PASSWORD -e SUR_BETA_PASSWORD \
  postgres psql -X -v ON_ERROR_STOP=1 -U postgres -d postgres <<'SQL'
\getenv bootstrap_password SUR_BOOTSTRAP_PASSWORD
\getenv alpha_password SUR_ALPHA_PASSWORD
\getenv beta_password SUR_BETA_PASSWORD
BEGIN;
CREATE ROLE sur_bootstrap LOGIN CREATEDB NOINHERIT PASSWORD :'bootstrap_password';
CREATE ROLE sur_alpha LOGIN PASSWORD :'alpha_password';
CREATE ROLE sur_beta LOGIN PASSWORD :'beta_password';
GRANT sur_alpha, sur_beta TO sur_bootstrap;
COMMIT;
SQL
```

Приложение последовательно создаёт отсутствующие базы через `Clients__N__BootstrapConnectionString`, применяет FluentMigrator и проверяет версии схемы рабочим подключением. При ошибке клиент получает 503 до устранения причины и повторного запуска. Другой клиент продолжает использовать свою базу. Повторный запуск применяет только отсутствующие миграции.

Для разделения полномочий можно задать `Clients__N__MigrationConnectionString` с ролью владельца схемы. В этом случае рабочая роль должна иметь право читать `VersionInfo` и выполнять нужные операции с таблицами. Для предварительно созданной базы служебную строку можно убрать. У клиента, его роли и его базы должен быть один владелец конфигурации, а приложение получает отдельные рабочие учётные данные каждого клиента. Compose предназначен для локального запуска и передаёт процессу выделенную роль CREATEDB.

## Контракты

- `GET /health/ready` на клиентском HTTPS-хосте возвращает 200 или 503 с ProblemDetails. Подготовка и проверка зависят от конкретной базы. Недоступность наблюдается при запросе readiness; если обнаружена отсутствующая миграция, клиент блокируется до повторного запуска.
- Маршруты Identity `/api/v1/public/…`, `/api/v1/provider/…` и `/api/v1/internal/…` сохраняют адреса. nginx закрывает `internal`. Issuer равен `https://<канонический-host>`, audience берётся из `Jwt__AccessTokenSettings__Audience`. Прежние токены потребуют повторного входа. Access JWT проверяется по issuer, а новые refresh-токены хешируются с issuer. Существующие записи сессий и хеши сохраняются в выбранной базе. RSA-ключи хранятся в постоянном томе; для переноса установки скопируйте текущую пару ключей до первого запуска.
- Новые ошибки границы используют ProblemDetails. Прежние бизнес-ответы Identity сохраняют форму. При добавлении новых списков используйте ограниченную страницу и детерминированную сортировку с уникальным полем. Прикладная составная запись передаёт общую транзакцию в SQL. Для новой изменяемой записи используйте условие по ожидаемой UUID-версии и возвращайте 409 при конфликте.
- HTTP-вебхуки выбирают клиента по тому же каноническому host до проверки секрета и чтения настроек. Будущий фоновый обработчик перечисляет `ClientDatabaseCatalog.Clients`, создаёт отдельный DI scope для каждого клиента и вызывает `ClientDatabaseContext.Select` до разрешения репозиториев. Прикладные webhook и фоновые сценарии добавляются вместе с соответствующим этапом.

## Identity и временный доступ

Для каждого клиента задайте `Clients__N__FirstAdministrator__Email` и `Clients__N__FirstAdministrator__FullName`. При старте они создают первого администратора один раз. Системный пользователь и каталог поставляются миграцией `202611140100`. Записи с одинаковым нормализованным email нужно устранить до применения миграции. Миграция не выбирает автоматически, какую учётную запись оставить.

SMTP использует STARTTLS. Настройте `Identity__Smtp__Host`, `Identity__Smtp__Port`, `Identity__Smtp__From`, а при необходимости `Identity__Smtp__Username` и `Identity__Smtp__Password`. Ошибка SMTP оставляет учётную запись и статус `FAILED`. Неподтверждённый `PENDING` старше двух минут возвращается как `FAILED`; повторная выдача создаёт новый пароль. Исходный пароль находится в памяти отправки. Для служебной повторной выдачи используйте `dotnet Api.dll --reissue-first-admin alpha.sur.test` в окружении бэкенда. Команда возвращает код 0 при успешной передаче письма SMTP.

Все приведённые ниже браузерные маршруты имеют префикс `/api/v1/public/connect/browser`. Получите CSRF-токен через `GET /csrf`, передавайте его в заголовке `X-CSRF-TOKEN` вместе с cookie при `POST /token`, `POST /token/refresh` и `POST /token/revoke`. Эти запросы выполняются с того же origin и без Authorization. Вход и refresh возвращают access JWT; храните его в памяти. Секрет обновления передаётся host-only cookie `Secure; HttpOnly; SameSite=Strict`. Для постоянства CSRF при перезапуске настройте закрытый каталог `Identity__DataProtectionDirectory`. Сессия с временным паролем допускает `PATCH /api/v1/public/users/change-password` с текущим и новым паролями. После смены войдите заново.

Административный API имеет префикс `/api/v1/provider`. `GET /roles`, `GET /roles/rights` и `PUT /roles/{roleId}` читают и сохраняют матрицу. `GET /users`, `GET /users/{userId}`, `POST /users`, `PATCH /users/{userId}`, `POST /users/{userId}/activate` и `POST /users/{userId}/reissue-access?version=…` работают с учётными записями. Изменения передают ожидаемую версию. Выдача возвращает карточку с текущим состоянием письма. Праву `admin` соответствует новый GUID, а ранее настроенные назначения с `ManageUsers` получают системную роль ADMIN при миграции. Для доступа со старым access JWT обновите токен или войдите заново. Снятые маршруты регистрации с заданным паролем, смены без текущего пароля и физического удаления возвращают 410.

`PUT /api/v1/provider/roles/catalog` синхронизирует системный каталог текущего клиента по данным запущенной версии бэкенда. Вызов выполняется администратором с действующей сессией и без тела запроса. Роли и права сопоставляются по системному коду. Обновляются названия, описания ролей и признак системной записи. Идентификаторы, активность, матрица прав и назначения пользователей сохраняются. Отсутствующие записи добавляются без назначений. Исходная матрица применяется только при первоначальном заполнении базы.

Успех возвращает 204. Повторный вызов с тем же каталогом сохраняет версии ролей. Изменение метаданных роли обновляет её версию, поэтому сохранение ранее открытой формы с предыдущей версией вернёт 409. Коллизия с существующей записью возвращает 409 с кодом `IDENTITY_CATALOG_CONFLICT` и откатывает обе части обновления.

Для приёмки на тестовой базе снимите состояние через `GET /roles` и `GET /roles/rights`, измените матрицу допустимой роли и вызовите синхронизацию дважды. Проверьте сохранение матрицы, активности и версий при повторном вызове. Для проверки обновления измените в тестовой базе название одной роли и одного права. После синхронизации ожидаются системные названия и прежние идентификаторы. Повторите вызов с обычной учётной записью и ожидайте 403.

Для проверки отката в тестовой базе освободите системное название одного права и присвойте это название другой записи. В той же базе измените название роли, чтобы синхронизации было что исправить. Вызов должен вернуть 409, а название роли должно остаться прежним. Для проверки конкуренции запустите два запроса синхронизации одновременно и сравните итоговые идентификаторы и версии с результатом одного успешного вызова.

### Внутренняя проверка сессии

Модули СУР вызывают `IAuthUseCaseManager.CheckSessionRightAsync` в текущем клиентском scope. Для прямого HTTPS-доступа к Kestrel предусмотрен `POST /api/v1/internal/sessions/check`. Внутренний вызывающий передаёт идентификаторы и версию из проверенного пользовательского токена и код права, заданный операцией. JSON содержит `userId`, `sessionId`, `accessVersion` и `rightCode`.

Служебный запрос передаёт `Authorization: SurInternal <ключ>`. Задайте уникальный случайный ключ для конкретного канонического хоста через конфигурацию `Identity:InternalKeys:<host>`, например `Identity__InternalKeys__alpha.sur.test`. nginx возвращает 404 на этот маршрут. Прямой вызов возвращает 204 для действующей сессии с правом, 401 при отказе служебной аутентификации и 403 при отказе проверки доступа. Проверка выполняется одним чтением клиентской БД. Внутренний HTTP-клиент может использовать `SystemRequestHttpHandler`, который передаёт ключ только настроенному HTTPS origin.
