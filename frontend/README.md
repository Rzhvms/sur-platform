# СУР · Angular

Angular 22.2, TypeScript 6.0.3, RxJS 7.8.2, Node.js 26.10.0 и npm 11.19.1. Точные версии указаны в `package.json`, `.nvmrc` и `package-lock.json`. Для Angular и TypeScript включены строгие проверки.

## Запуск

```sh
cd frontend
nvm use
npm ci
npm run check
npm test
npm run preview
```

Откройте `http://localhost:4200/demo/risks` для просмотра с синтетическими данными. Для работы с клиентской базой используйте HTTPS и зарегистрированный адрес API.

```sh
SUR_API_ORIGIN=https://alpha.sur.test \
SUR_API_CA=/absolute/path/to/test-ca.pem \
SUR_TLS_CERT=/absolute/path/to/localhost-cert.pem \
SUR_TLS_KEY=/absolute/path/to/localhost-key.pem \
npm start
```

UI открыт на `https://localhost:4200`. Сертификат UI должен содержать `localhost` и быть доверенным браузером. Имя upstream должно разрешаться локально и совпадать с сертификатом API и зарегистрированным клиентом. Для прямого локального Kestrel можно указать `https://localhost:7224`, если `localhost` зарегистрирован у клиента. `SUR_API_CA` нужен для выделенного тестового УЦ. Проверка цепочки и имени upstream включена. Для локального запуска браузерные запросы используют относительные пути; прокси берёт upstream из конфигурации, подставляет его Host и очищает клиентские forwarding-заголовки. После смены клиента остановите процесс и очистите cookies локального UI или используйте отдельный профиль браузера.

| --- | --- | --- |
| `/` | Переход в реестр | Через проверку сессии |
| `/login` | Вход | Браузерные CSRF и token |
| `/change-password` | Смена временного пароля | `PATCH /api/v1/public/users/change-password` |
| `/forbidden` | Отказ в доступе | Проверка эффективных прав |
| `/risks` | Реестр | `GET /api/v1/public/risks` |
| `/risks/board` | Доска | `GET /api/v1/public/risks/board`, отдельные страницы через `/board/{columnStatus}` |
| `/risks/:id` | Паспорт, обсуждение, меры и пересмотры | `GET /api/v1/public/risks/{id}` и связанные списки |
| `/risks/new`, `/risks/:id/edit` | Создание черновика и редактирование паспорта | `POST /risks` и `PUT /risks/{id}` с версией карточки |
| `/demo/risks`, `/demo/risks/board`, `/demo/risks/:id` | Три прототипа, например `/demo/risks/R-1042` | Общий локальный набор. В реестре и на доске можно переключить примеры загрузки, пустого списка и ошибки |
| `/treatments`, `/treatments/:id` | Переход к реестру рисков и карточка меры | `GET /api/v1/public/treatments/{id}`, согласования, назначения, статусы и комментарии |
| `/approvals` | Очередь согласований | `GET /api/v1/public/treatment-approvals` и команды по версии запроса |
| `/admin/jira` | Настройка и журнал Jira | `/api/v1/provider/jira` для администратора |
| `/admin/users`, `/admin/users/:id`, `/admin/users/new` | Список, карточка и создание пользователя | `/api/v1/provider/users` |
| `/admin/roles` | Системные роли и права | `/api/v1/provider/roles` |
| `/admin/organization` | Дирекции, сотрудники, процессы, объекты и назначения | `/api/v1/provider/organization` |
| `/admin/risk-settings` | Справочники, шкалы и пороги | Реестры провайдера |
| `/admin/reviews` | Расписания, вебхуки и история запусков | Источники пересмотра провайдера |
| `/reports` | Снимок рисков и экспорт CSV/XLSX | `POST /api/v1/public/documents/reports`, статус и строки по курсору |
| `/imports` | Импорт CSV и результаты строк | `POST /api/v1/public/documents/imports`, загрузка и сопоставление |
| `/admin/history` | Журнал изменений и выгрузка JSON | `GET /api/v1/provider/business-history`, `POST /api/v1/provider/documents/history` |

Реестр и доска восстанавливают поиск, сортировку, статус и страницу из URL. Дополнительные фильтры по дирекции, процессу, владельцу, объекту и категории передаются на сервер как идентификаторы. Подсказки для этих полей берутся из просмотренных карточек. Фильтр можно также открыть по ссылке с нужным идентификатором. Независимые смещения колонок хранятся в URL как `column_<STATUS>`. При смене фильтра они сбрасываются. Черновик заметки в демонстрационной карточке хранится в памяти экземпляра карточки. Access JWT и эффективные права хранятся в памяти вкладки, refresh-cookie выдаёт сервер.

## Проверка сессии на HTTPS-стенде

Используйте тестовые аккаунты и актуальную сборку API. Для авторизации требуется браузер с Web Locks. Один lock на origin сериализует вход, refresh и выход вместе с получением CSRF. В браузере без Web Locks автоматическое восстановление и вход отключены. BroadcastChannel передаёт только сигнал завершения сессии. В Web Storage сохраняется только булев признак незавершённого отзыва, который блокирует автоматическое восстановление после сетевого сбоя при выходе.

1. Войдите через `/login`, затем откройте защищённую глубокую ссылку в новой вкладке и перезагрузите обе вкладки. В Network проверьте, что перед каждым POST в `/connect/browser` есть GET `/csrf`, запросы несут `X-CSRF-TOKEN`, а после входа и refresh запрашивается `/users/me`. Проверьте, что access JWT отсутствует в Web Storage.
2. Выполните [сценарии проверки CSRF](../backend/Apps/SurPlatform/Tests/Http/browser-session.http) на отдельной тестовой сессии. Проверьте отказ без заголовка, ротацию refresh-cookie и отказ восстановления после отзыва. У cookie ожидаются `HttpOnly`, `Secure`, `SameSite=Strict`, `Path=/` и отсутствие атрибута `Domain`.
3. Выйдите в одной вкладке и проверьте переход второй вкладки ко входу. Повторите с отключённой сетью и проверьте сообщение о неподтверждённом выходе. После восстановления сети нажмите «Повторить выход».
4. Войдите с временным паролем. Проверьте переход на `/change-password`, запрет прямого открытия реестра, смену пароля и новый вход. Проверьте истечение access JWT и отзыв сессии. При истечении GET повторяется один раз после refresh. При отзыве требуется вход.
5. Войдите пользователем без административного права и откройте `/administration` напрямую. Ожидается `/forbidden`. Отзовите право на сервере при открытом разделе и выполните чтение. При отказе SPA заново запрашивает доступ, а при утрате права закрывает раздел.
6. Откройте два зарегистрированных тестовых имени на разных origins. Убедитесь, что вход или выход у одного клиента не меняет cookie другого. При локальной разработке один Angular origin соответствует одному клиенту. Для параллельного тестирования разных клиентов используйте разные имена и сертификаты или отдельные профили браузера.

Политика палитры для первого дизайна закреплена в компоненте оценки и применяется одинаково в реестре, доске и карточке. Монохромные концепции знака и бриф находятся в [design](design/brief.md), демонстрация в [preview.html](design/preview.html).

## Проверка реестра и карточки на HTTPS-стенде

1. Подготовьте действующие группу и опасность, категорию и процесс для тестового пользователя. В `/risks/new` проверьте список доступных процессов и создайте черновик. Найдите его по названию в реестре и на доске. Черновик должен быть только в колонке «Черновик».
2. Подготовьте более восьми совпадений в одной колонке. Убедитесь, что переход дальше запрашивает только `/board/{columnStatus}` с прежними фильтрами и новым `offset`. Итог по колонке сохраняется, соседние колонки остаются на своих страницах. Смена фильтра сбрасывает страницы. Открытие карточки клавишей Enter и возврат сохраняют URL.
3. Проверьте отсутствие результатов, пустую колонку, пустую доску, загрузку и ошибку сервера. На HTTPS-стенде дополнительно откройте отсутствующий ID и повторите чтение после отзыва права просмотра.
4. Откройте редактирование в двух вкладках и сохраните разные изменения. При `409` сверяйте свежий паспорт с сохранённым черновиком. Продолжение использует свежую версию только после явного подтверждения. Если после первой оценки сервер запрещает редактирование, дальнейшее сохранение недоступно.
5. Добавьте, измените и удалите свой комментарий. Проверьте комментарий другого автора под обычной ролью, системный комментарий под администратором и конфликт версии в двух вкладках. Введите HTML как обычный текст и убедитесь, что он отображается буквально. Проверьте раздельные блоки текущей и предыдущей оценок на карточке пересматриваемого риска.

Серверные запросы для проверки доступны в [risks.http](../backend/Apps/SurPlatform/Tests/Http/risks.http).

## Проверка оценок, решений и пересмотра на HTTPS-стенде

1. Опубликуйте тестовую денежную шкалу и откройте черновик под владельцем основного процесса с правами оценки и редактирования. Проверьте риск без объекта с нулевой суммой и риск с объектом с нулевым простоем. Подтвердите preview. Риск должен стать активным, ноль виден в текущей оценке и истории, а матрица содержит 25 положительных ячеек. Откройте историческую оценку и сверьте ID её шкалы с запросом `/impact-scale/{id}`.
2. Замедлите запрос preview и измените поле до его завершения. Кнопка подтверждения прежнего результата должна остаться недоступной. Затем получите preview и опубликуйте другую версию шкалы в соседней вкладке. Сохранение должно вернуть `409`. Обновите карточку, рассчитайте повторно и явно подтвердите новый результат. Аналогично проверьте параллельное сохранение и изменение ставки объекта.
3. Проверьте каждую команду на отдельном подходящем риске. Для разделения выберите минимум два процесса и один основной. Для передачи используйте кандидата из API. Под ролью без права команды кнопка недоступна. Под ролью с правом, но без нужного назначения, API возвращает отказ. Если операцию блокируют меры, интерфейс показывает идентификаторы блокирующих мер.
4. Закройте риск с причиной. Верните закрытый риск на пересмотр с подтверждением и снова откройте историю. Карточка отличает отсутствие оценки от ожидания оценки владельца. История отдельно показывает состояние запуска и состояние риска в запуске, а также сохранённый источник. Вернитесь к отфильтрованному реестру или доске и проверьте обновлённое состояние.

HTTP-сценарии находятся в [risk-assessment.http](../backend/Apps/SurPlatform/Tests/Http/risk-assessment.http) и [risk-reviews.http](../backend/Apps/SurPlatform/Tests/Http/risk-reviews.http).

## Проверка мер и Jira на HTTPS-стенде

1. На активном риске в режиме обработки создайте меру под пользователем с `create_treatment`. Проверьте выбор любой активной связи, редактирование черновика владельцем и сравнение версий в двух вкладках.
2. Отправьте меру на согласование. В очереди проверьте серверный счётчик, сохранённый уровень и пороги. Попробуйте отказ и отзыв с пробельной причиной. Выполните параллельное решение в двух вкладках, сверьте обновлённый счётчик и историю.
3. Назначьте исполнителя командой передачи в ожидание и запустите меры из карточки риска. При ручном управлении проверьте замену, приостановку, возобновление, завершение без фактических расходов и отмену. После последней активной меры сверьте статус родительского риска. При отзыве права в открытой форме проверьте отказ от команды и обновление доступных действий.
4. В изолированном клиенте с тестовой Jira измерьте задержку от изменения задачи до отображения на открытой вкладке. Проверьте предел 60 секунд, отсутствие фоновых запросов со скрытой вкладки и обновление при возвращении. Проверьте отдельные состояния ожидания, отсрочки и `UNKNOWN`, сверку найденной задачи, подтверждение отсутствия, отказ для устаревшей попытки и сохранение терминального статуса.
5. При сбое Jira до POST откройте карточку заново под инициатором и вторым пользователем с правом чтения. После запуска набора уведомление видно на риске, после ручного возобновления — на мере. При восстановлении Jira уведомление исчезает. Для серверной проверки используйте [jira-retry-notice.http](../backend/Apps/SurPlatform/Tests/Http/jira-retry-notice.http).

## Проверка администрирования

1. Под администратором создайте дирекцию и пользователя с оргданными. В двух вкладках проверьте одну свободную позицию, займите её первой командой и отправьте вторую. Сверьте отсутствие частично созданного пользователя и состояние повторной проверки позиции.
2. На карточке пользователя проверьте отображение процессов и назначений перед деактивацией, отдельную активацию записи сотрудника и статус повторной выдачи доступа. Проверьте перевод сотрудника на свободную дирекцию и отказ перевода при действующем процессе.
3. Откройте роль в двух вкладках. После сохранения первой формы вторая должна получить конфликт и перечитать каталог. Проверьте ограничения ADMIN и недоступность разделов под обычной ролью.
4. Создайте группу, опасность и категорию. Опубликуйте шкалу с подтверждением и настройте границы принятия. Создайте недельное и одноразовое расписания и проверьте даты без смещения.
5. Создайте и ротируйте вебхук пересмотра. Секрет виден только в ответе на эти команды и текущей форме, исчезает при уходе. Проверьте `Cache-Control: no-store` и отсутствие секрета в URL и GET. Для Jira отдельно проверьте пустую настройку, выключенный обмен и отказ проверки. После отказа восстановления перечитайте панель под инициатором и вторым администратором.
6. На узкой и широкой вкладках проверьте переход по секциям, подписи полей, клавиатурный доступ и горизонтальное переполнение. [Контрактные запросы](../backend/Apps/SurPlatform/Tests/Http/admin-frontend.http).

## Проверка отчётов, истории и импорта

Используйте изолированного HTTPS-клиента с nginx и тестовым закрытым MinIO. [Сценарии API](../backend/Apps/SurPlatform/Tests/Http/documents.http).

1. На `/reports` сравните текущий срез и исторический срез со смещением `+05:00` до известного изменения риска. Сверьте момент среза, фиксацию снимка и формирование файла. Пролистайте снимок вперёд и назад, проверяя курсоры `after`. С правом экспорта скачайте CSV и XLSX. После отзыва `export_report` повторите скачивание.
2. На `/admin/history` покажите пустой диапазон дат UTC и сформируйте выгрузку. Она должна содержать `[]`. В диапазоне с событиями проверьте постраничность и возможность открыть задание из URL.
3. На `/imports` выберите UTF-8 CSV с многострочным полем в кавычках и строкой с недопустимым ID справочника. Сверьте SHA-256 и размер с исходными байтами. В DevTools проверьте `PUT /file` с `application/octet-stream` и телом файла. Успешная загрузка через nginx подтверждает, что Kestrel получил положительный `Content-Length`, совпадающий с зарегистрированным размером. Контроллер отклоняет запрос без длины.
4. Имитируйте потерю ответа регистрации после коммита. Повторите команду из открытой формы и проверьте тот же `operationId` и ID задания. Скопируйте URL с `?job=`, откройте его в другой вкладке под тем же аккаунтом и продолжите с подтверждённой стадии. Проверьте тот же CSV при незавершённой загрузке и считывание серверного источника для предпросмотра при сопоставлении.
5. Запустите импорт. Проверьте частичный успех, счётчики, ошибки строк и ссылку на созданный риск. На временном сбое проверьте повтор при `canRetry`. Убедитесь, что опрос завершается по терминальному состоянию, при отказе доступа и при уходе со страницы. Под другим пользователем или в другом клиенте проверьте отказ доступа к скопированному ID.

## Выпуск

После разрешённой сборки `npm run build` результат лежит в `dist/sur/browser`. Используйте его как статический каталог nginx. Для текущего Compose добавьте override и убедитесь, что собранный каталог существует.

```sh
cd backend
docker compose -f docker-compose.yml -f ../frontend/deploy/compose.spa.yml up -d --no-build
```

Конфигурация nginx обслуживает глубокие ссылки через `index.html`. Префиксы API, health и Swagger идут к бэкенду, внутренние REST-маршруты возвращают 404. После публикации проверьте `/demo/risks/R-1042` и неизвестный `/api/v1/public/unknown`: первая ссылка отдаёт SPA, вторая — HTTP-ответ бэкенда.
